# Releases

Releases are fully automated; nobody tags by hand. On every push to `main`, after the tests pass:

1. The **Version** job calculates the next version with `versinc` itself.
2. If it differs from the latest tag, the **Release** job (in `ci.yml`) uses a GitHub App
   installation token to commit the bumped version in `Cargo.toml`, `Cargo.lock`, the action's
   default `version` input (`action.yml`) and the action pins in the README and
   [GitHub Action](github-action.md) examples as `chore(release): vX.Y.Z`, create the tag
   `vX.Y.Z`, and push both atomically. If `main` moved in the meantime, nothing is pushed and the
   next run releases instead.
3. The tag push starts
   [`release.yml`](https://github.com/lucasgomes-eti/version-included/blob/main/.github/workflows/release.yml),
   generated by [dist](https://github.com/axodotdev/cargo-dist), which builds the three targets
   natively, generates the shell installer and checksums, and publishes a GitHub Release.
4. After the release is published, `release.yml` calls `action-test.yml`, which tests the action
   against the new binaries, and
   [`site.yml`](https://github.com/lucasgomes-eti/version-included/blob/main/.github/workflows/site.yml),
   which builds the [site](development.md#documentation-site) from the release's tag and
   deploys it to GitHub Pages.

The App token matters: pushes made with the default `GITHUB_TOKEN` don't start other workflows,
so a tag pushed with it would never trigger `release.yml`. The release commit is a `chore`, so the
CI run it starts calculates the same version and releases nothing.

The version a merge produces depends on its commits (see
[Commit rules](how-it-works.md#commit-rules)), so with **squash merging** the pull request title
must follow the commit convention (e.g. `feat(release): …`); with merge commits or rebase merging,
the branch's own commits count and the merge commit itself is ignored.

## dist

`release.yml` and `dist-workspace.toml` are managed by dist: change `dist-workspace.toml` and run
`dist generate` instead of editing `release.yml`, otherwise dist's check on pull requests fails.
Install dist with `cargo install --git https://github.com/axodotdev/cargo-dist --tag v0.33.1
cargo-dist --locked` (the version pinned as `cargo-dist-version`).

## Release bot setup

The Release job needs a GitHub App that can push to this repository:

1. Create a GitHub App (Settings → Developer settings → GitHub Apps → New GitHub App) with
   webhooks disabled and the single repository permission **Contents: Read and write**.
2. Install it on this repository only.
3. In the `main` environment, add the App's Client ID as the variable `RELEASE_APP_CLIENT_ID` and
   a generated private key as the secret `RELEASE_APP_PRIVATE_KEY`.

Restrict the `main` environment to the `main` branch (Deployment branches and tags → Selected
branches) so only workflows running on `main` can use the App's key.

## Site publishing

The site is published at <https://lucasgomes-eti.github.io/version-included/>. `site.yml` builds
it on pull requests without deploying, deploys it after every release, and can be run by hand
(Actions → Site → Run workflow) to republish, for example after a docs-only change, which doesn't
cause a release. A manual run from `main` publishes `main`'s docs, which may describe changes that
aren't released yet.

GitHub Pages setup:

1. Settings → Pages → Build and deployment → Source: **GitHub Actions**. This creates the
   `github-pages` environment.
2. Settings → Environments → `github-pages` → Deployment branches and tags: keep `main` and add the
   tag rule `v*`. The deploy runs on the release's tag, which the default rule (the default branch
   only) rejects.

dist gives the `site` job the `pages: write` and `id-token: write` permissions that deploying
needs (`github-custom-job-permissions` in `dist-workspace.toml`); without them the called workflow
can't request more than `release.yml`'s `contents: write`.
